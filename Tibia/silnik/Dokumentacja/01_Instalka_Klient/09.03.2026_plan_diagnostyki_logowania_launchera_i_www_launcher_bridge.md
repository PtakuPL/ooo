## 1. Problem

Na dzien `2026-03-09`:

- logowanie na stronie `RedDAXE.pl` dziala,
- logowanie w launcherze nadal nie dziala,
- problem wystepuje co najmniej dla dwoch kont, wiec nie wyglada juz na pojedynczy uszkodzony rekord konta,
- UI launchera pokazuje glownie ogolny komunikat `Logowanie konta nie powiodlo sie. Sprobuj ponownie.`

To oznacza, ze temat trzeba rozdzielic na:

1. realna diagnoze miejsca awarii w launcherze,
2. osobny UX/debug bridge `WWW -> launcher`, zeby latwiej odtworzyc i izolowac problem.

## 2. Co juz wiemy z kodu i lokalnej diagnostyki

### 2.1 Hipoteza `freshInstall` nie jest juz wystarczajaca

Poprzedni plan zakladal, ze login psuje sie przez `CLIENT_LOCKED + brak launchToken` dla fresh installa.

Ale aktualny kod pokazuje, ze:

- launcher wysyla juz `freshInstall=true` w `launcher-rust/crates/launcher-api/src/client.rs`,
- launcher ma juz retry dla bledow `LCH_TOKEN*` w `launcher-rust/apps/launcher-tauri/src/commands.rs`,
- `login.php` ma juz wyjatek: jesli `CLIENT_LOCKED=true`, ale `freshInstall=true`, to token nie jest wymagany.

Wniosek:

- plan `freshInstall-only` jest nieaktualny jako glowna diagnoza,
- nawet jesli ten problem kiedys istnial, to nie tlumaczy juz obecnego stanu.

### 2.2 Lokalna strona i launcher uzywaja dwoch roznych originow, ale w tym dev srodowisku trafiaja w te sama maszyne

To byla mocna hipoteza na poczatku analizy, ale zostala doprecyzowana.

Dowody:

- lokalna strona, z ktorej korzystasz w debugu, dziala pod `https://127.0.0.1`,
- launcher UI ma `WEBSITE_BASE_URL = "https://127.0.0.1"`,
- bootstrap i domyslne `launcher_config.json` dalej wskazuja `apiBaseUrl = "https://tibia.reddaxe.pl/apik/v1"`,
- ale w aktualnym dev srodowisku `tibia.reddaxe.pl` rozwiazuje sie do `127.0.0.1`.

Wniosek:

- to nie wyglada juz na dwa rozne backendy,
- bardziej wyglada to na ta sama lokalna instancje dostepna pod aliasem domenowym,
- a glownym kandydatem na problem staje sie roznica TLS / trust store / self-signed cert dla domeny `tibia.reddaxe.pl`.

### 2.3 Lokalny backend loginu przyjmuje juz poprawne konto

Z aktualnej lokalnej diagnostyki:

- `RedDAXE` login z dzialajacym kontem przechodzi,
- lokalny `login.php` zapisuje w `/tmp/login_debug.log` poprawne dopasowanie hasla i zwraca `session`,
- stary incydent z kontem `1021` byl osobnym problemem danych, ale nie tlumaczy juz obecnego faila launchera.

Wniosek:

- obecny problem launchera nie wyglada juz na zwykle `wrong credentials` po stronie lokalnego API.

### 2.4 Launcher chowa za malo informacji diagnostycznych

Launcher ma mapowanie kodow backendu, ale UX nadal bywa zbyt ogolny:

- UI konczy na `alerts.accountLoginErrorGeneric`,
- user nie zawsze widzi:
  - jakiego `api_base_url` uzyto,
  - jaki byl `lchCode`,
  - czy padl `launchToken`,
  - czy to byl problem transportu/TLS, czy odpowiedzi API.

To nie musi byc glowna przyczyna awarii, ale utrudnia diagnoze.

## 3. Najbardziej prawdopodobne przyczyny w tej chwili

Kolejnosc od najbardziej prawdopodobnej:

### H1 - Lokalny alias domenowy + self-signed cert

Launcher uzywa `https://tibia.reddaxe.pl/apik/v1`, a lokalna strona debugowa pracuje na `https://127.0.0.1`.

W aktualnym dev srodowisku `tibia.reddaxe.pl` rozwiazuje sie do `127.0.0.1`, wiec to nie musi byc inny backend. Bardziej prawdopodobny jest taki scenariusz:

- launcher trafia do lokalnego API po aliasie domenowym,
- ale widzi self-signed cert dla `tibia.reddaxe.pl`,
- i odrzuca polaczenie, jesli nie ma jawnego `devMode` albo wyjatku dla loopback aliasu.

### H2 - Runtime config uruchomionego launchera nie jest tym, co zakladamy

Nawet jesli repo ma jeden config, uruchomiony launcher moze miec inny `launcher_config.json` w katalogu instalacji lub profilu usera.

Trzeba potwierdzic:

- `apiBaseUrl`,
- `profile`,
- `devMode`,
- `launcherDataDir`,
- czy runtime launcher czyta config z miejsca, ktore faktycznie sprawdzamy.

### H3 - Login pada po drodze, ale UI chowa szczegol

Mozliwe sa jeszcze:

- blad TLS / cert / host mismatch,
- blad `launcher-token.php`,
- blad `account-context.php` po udanym loginie,
- brak `sessionkey` po stronie response parsing,
- inny blad backendowy, ktory nie jest jasno pokazany userowi.

## 4. Idea: przycisk WWW -> launcher po zalogowaniu

Pomysl usera jest dobry i nie trzeba go budowac od zera.

W systemie juz sa gotowe klocki:

- `RedDAXE` ma `/reddaxe/post-login.php`,
- strona potrafi juz wygenerowac `WWW -> launcher sync token`,
- endpoint `account-sync-www-token.php` zwraca:
  - `syncToken`
  - `consumeEndpoint`
  - `launcherDeepLink`
- istnieje tez `account-sync-consume.php`.

Czyli techniczny fundament juz istnieje, ale UX jest jeszcze debugowy.

## 5. Docelowy kierunek produktu

Po zalogowaniu na `RedDAXE.pl` user powinien miec czytelna akcje:

- `Zaloguj sie na launcher`
- albo `Odpal launcher`

Flow docelowy:

1. user loguje sie na `RedDAXE.pl`,
2. klika `Zaloguj sie na launcher`,
3. strona pobiera jednorazowy `WWW -> launcher sync token`,
4. strona otwiera `launcherDeepLink`,
5. launcher konsumuje token przez `account-sync-consume.php`,
6. launcher dostaje juz poprawna sesje bez recznego wpisywania hasla.

Korzyci:

- latwiejsza diagnoza, czy problem lezy w formularzu email+haslo, czy w samym kanale sync,
- lepszy UX dla usera,
- mniejsza liczba miejsc, gdzie user moze wpisac zle dane,
- jeden bardziej kontrolowany flow dla `WWW <-> launcher`.

## 6. Co trzeba ustalic zanim to wdrozymy

### 6.1 Czy launcher ma byc logowany tylko przez haslo, czy tez przez WWW bridge

Opcje:

- haslo zostaje jako podstawowy flow, a `WWW -> launcher` jest tylko pomocnicze,
- albo `WWW -> launcher` staje sie preferowanym flow po web loginie,
- albo oba flow istnieja rownolegle.

Rekomendacja:

- na teraz oba flow rownolegle,
- ale bridge ma byc narzedziem diagnostycznym i produkcyjnym fallbackiem.

### 6.2 Czy launcher ma rejestrowac custom URI scheme

Do wygodnego `Odpal launcher` potrzebny jest stabilny scheme, np.:

- `reddaxe://account-sync?token=...`

Trzeba dopiac:

- rejestracje scheme na Windows,
- fallback, jesli launcher nie jest zainstalowany,
- obsluge klikniecia z przegladarki.

### 6.3 Jak pokazywac userowi bledy

Trzeba zdecydowac:

- czy w dev pokazujemy surowy `lchCode`,
- czy w prod tylko ladny komunikat + eksport logow,
- czy `RedDAXE` ma miec widok `launcher sync diagnostics`.

## 11. Dalsze wdrozenie `WWW -> launcher`

Po pierwszej poprawce TLS / diagnostyki zostal wdrozony tez produktowy most `WWW -> launcher`.

### 11.1 Co zostalo zmienione

1. Launcher dostal obsluge `launcher://account-sync?token=...`:
   - token moze przyjsc przy starcie jako argument CLI,
   - jesli launcher juz dziala, drugi proces zapisuje token do lokalnego pliku `pending_account_sync_token.txt` i konczy sie,
   - aktywny launcher konsumuje taki token przy starcie, focusie i cyklicznym pollingu.

2. Launcher konsumuje `WWW -> launcher sync token` przez `account-sync-consume.php`:
   - zapisuje `sessionKey`,
   - przechodzi do trybu zalogowanego bez recznego wpisywania hasla,
   - pokazuje osobny komunikat sukcesu / bledu synchronizacji WWW.

3. `RedDAXE` `post-login.php` przestal byc debugowym generatorem tokena:
   - przycisk zmieniono na `Uruchom launcher` / `Open launcher`,
   - strona dalej pobiera token z `account-sync-www-token.php`,
   - ale zamiast wyswietlac raw `syncToken`, probuje od razu otworzyc lokalny launcher przez `launcherDeepLink`,
   - zostawia fallback `Pobierz launcher`.

4. Bootstrap instalatora na Windows rejestruje teraz `launcher://`:
   - instalacja zapisuje scheme w `HKCU\\Software\\Classes\\launcher`,
   - uninstall usuwa scheme razem z kluczem uninstallera,
   - launcher nadal robi tez `best-effort` rejestracje przy starcie.

### 11.3 Co juz bylo wdrozone po stronie anty-spam

Podejrzenie, ze login / rejestracja nie maja zadnych blokad, okazalo sie nieaktualne.

Juz przed tym etapem backend mial aktywne rate limiting:

- [login.php](/var/www/html/apik/v1/login.php)
  - `login:ip` = `30` prob / `60s`
  - `login:email` = `10` prob / `60s`

- [register-account.php](/var/www/html/apik/v1/register-account.php)
  - `register:ip` = `3` rejestracje / `3600s`

- [common.php](/var/www/html/apik/v1/common.php)
  - wspolny helper `applyRateLimit()`

- [account-sync-www-token.php](/var/www/html/apik/v1/account-sync-www-token.php)
  - limit otwartych tokenow WWW -> launcher per konto

Wniosek:

- na tym etapie nie dokladano nowego rate limitingu dla loginu / rejestracji,
- prace skupily sie na `WWW -> launcher` i lepszej diagnostyce launchera.

   - ale nadal brakuje:
     - czytelnego cooldownu / `retry after`,
     - rozroznienia login vs rejestracja w osobnym komponencie UX,
     - bardziej jawnego komunikatu, czy limit jest per IP czy per konto.

2. `RedDAXE` login / rejestracja:
   - strona pokazuje backendowy blad z API,
   - wiec technicznie komunikat jest widoczny,
   - ale nadal brakuje:
     - osobnego stylu / stanu `rate limited`,
     - lokalnego odliczania czasu oczekiwania,
     - bardziej produktowego copy zamiast surowego `[code] ... (HTTP ...)`.

3. `WWW -> launcher`:
   - przycisk `Uruchom launcher` jest juz produktowy,
   - ale bez nowego buildu i deployu `.exe` user nie zobaczy efektu end-to-end.

Wniosek praktyczny:

- backendowe zabezpieczenia juz istnieja,
- launcher czesciowo umie je pokazac,
- najwieksza luka jest teraz w czytelnosci i widocznosci tego stanu dla usera, a nie w samym braku rate limitingu.

### 11.5 Otwarte rzeczy po tej fazie

- trzeba wykonac realny test end-to-end na Windows:
  1. instalacja przez bootstrap
  2. klik `Uruchom launcher` po web loginie
  3. przejecie tokena przez launcher
  4. wejscie do trybu zalogowanego bez recznego hasla
- trzeba potwierdzic zachowanie przy:
  - launcher juz uruchomiony
  - launcher nie jest zainstalowany
  - token wygasl lub zostal juz zuzyty
- trzeba wdrozyc nowe artefakty launchera i bootstrapa, bo obecny zainstalowany `.exe` jeszcze nie ma tej logiki
- trzeba dodac lepszy UX dla `rate limited` na `RedDAXE`:
  - bez surowych `[errorCode]`
  - z czytelnym komunikatem i ewentualnym countdownem
- trzeba zdecydowac, czy `Uruchom launcher` ma miec dodatkowy fallback:
  - `Skopiuj token`
  - albo `Otworz launcher recznie i wroc do strony`

## 12. Najwazniejsze problemy, ktore dalej widac

1. Najwiekszy blocker praktyczny:
   - kod jest gotowy,
   - ale bez rekompilacji i wdrozenia Windowsowych artefaktow nie da sie potwierdzic realnego dzialania `launcher://` u Ciebie.

2. Najwieksza luka UX:
   - `RedDAXE` login / rejestracja nadal pokazuja backendowy blad dosc surowo,
   - to dziala diagnostycznie, ale nie jest jeszcze ladnym produkcyjnym komunikatem.

3. Najwieksza luka testowa:
   - nie bylo jeszcze realnego testu przegladarka -> zainstalowany launcher -> consume token -> zalogowany launcher.

4. Najwieksza luka produktowa:
   - strona nie wykrywa jeszcze, czy launcher rzeczywiscie sie otworzyl,
   - wiec fallback po kliknieciu `Uruchom launcher` jest nadal tylko posredni.
